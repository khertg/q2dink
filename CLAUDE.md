# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Q2Dink is a free, offline-first pickleball open-play manager (product spec: `docs/pickleq-specs.md`, user-facing overview: `README.md`). npm-workspaces monorepo: `apps/web` (React 19, Vite, Tailwind v4, shadcn/ui, Zustand, Dexie), `apps/api` (Fastify + Postgres), `packages/shared` (wire contract used by both), `deploy/` (Caddy + API + Postgres).

## Commands

Run from the repo root unless noted. Each script runs in every workspace that defines it.

- `npm run dev` (web), `npm run dev -w @q2dink/api` (API on 8787, embedded PGlite, no database needed), or `docker compose up` (web 5173 + API + Postgres + Adminer on 8080, hot reload)
- `npm test`, `npm run typecheck`, `npm run build`
- `npm run lint` (root only, oxlint over `apps packages`; workspaces have no lint script)
- One unit test: `cd apps/web && npx vitest run src/rotation/engine.test.ts -t "part of the name"` (same in `apps/api`, `packages/shared`)
- E2E: `cd apps/web && npx playwright test e2e/session.spec.ts --project=desktop`. Flags do not pass through `npm run test:e2e --`; call `npx playwright test` directly. Projects: `desktop`, `mobile`, `cloud`, `cloud-mobile` (cloud specs live in `e2e/cloud/` and run against a second build plus a real API on port 8788 that Playwright starts). First run needs `npx playwright install chromium`.
- API on real Postgres: `TEST_DATABASE_URL=postgres://... npx vitest run` in `apps/api`. That suite **drops the `public` schema**, so point it at a throwaway database, never the dev one.

Node 24 (CI and both Dockerfiles use it; built with Node 26). CI (`.github/workflows/ci.yml`) runs unit, API-on-Postgres, docker, e2e and prod-smoke jobs; prod-smoke starts `deploy/docker-compose.prod.yml` with `DOMAIN=:80` and runs `bash deploy/smoke.sh <url>` (headers, client routes, `/api/health`, service worker). You can run the same script against a local prod stack: `DOMAIN=:80 HTTP_PORT=8090 POSTGRES_PASSWORD=x docker compose -p smoke -f deploy/docker-compose.prod.yml up -d --build`, then `bash deploy/smoke.sh http://localhost:8090`, then `down -v`.

## Architecture

### The rotation engine is pure; the store is a thin wrapper
`apps/web/src/rotation/engine.ts` holds every session rule as pure, immutable functions over `SessionState` (`rotation/types.ts`); `store/session.ts` (Zustand + persist to localStorage) only calls them. Undo is the store keeping `previous`, which almost every action clears; settings-like actions (`setAvgGameMinutes`, `setPlayerSkill`) instead carry their change into `previous`. The engine never reads the clock: the store passes `now`.

Behaviours that span several files:
- **The session clock** (`rotation/types.ts`: `notStarted`, `clockStoppedAt`, `pausedBy`, `startedAt`/`startedBy`, `resumedBy`; `rotation/clock.test.ts`). A session is **created not started** (`markNotStarted`: `clockStoppedAt` = creation time): players check in and courts can be set up, but `startGame` throws, it is never live (`isLive`, `setLive(true)` throws) and no time runs. **Start session** (`startSessionClock`) and **Resume** (`resumeSession`) shift every running timer by the stop (`runClock` -> `shiftSessionClock`), so the stop never counts as waiting or playing; **Pause** (`pauseSession`) sets `clockStoppedAt` again (a second pause is a no-op, so two devices agree on the first). While stopped, **every action's `now` becomes `sessionNow`** (= `clockStoppedAt`), applied once in `applyAction`, and the UI reads the frozen time through `SessionClockContext`/`useSessionNow` (`lib/time.ts`). Finishing a game while paused is allowed (its time stops at the pause). The actions are `startClock`/`pause`/`resume`; who did it comes from `deviceRef()` (`lib/device.ts`). Old sessions have none of the fields: running.
- **Nothing starts by itself.** Staff press Start game. `nextGroup()` computes the group (matchmaking in `matchmaking/grouping.ts`), `startGame()` puts it on a court. The same `nextGroup()` feeds the Next up card, the queue badges and the published live board, so what staff see is what starts. `fillCourts` in `rotation/testing.ts` is a test-only helper.
- **Next up can be hand-picked** (`nextUpPick`, Team A then Team B, kept in that order so a swap never reshuffles the others); it is honoured only while every member still waits and is cleared by anything that removes them from the queue. **Anyone can be swapped in from any card** (`replaceNextUp`, `replacePlayer`): a player waiting, on a break (checked back in), in the same group or on the same court (they change places), or on another court (they trade places). The swap dialog lists everyone with where they are (`lib/playerStatus.ts`). Each player tile on a court or in Next up has a ⋮ menu (`PlayerMenu`: Swap…, Remove from court / Remove from Next up, Take a break, Remove from session); the first three keep the player in the session. In Next up, Remove/break put a stand-in (`nextUpStandIn`, `dropFromNextUp`) in the exact spot. **Remove from session** (`removePlayer`, also in the ⋮ menu of waiting players (`WaitingPlayerMenu`, on the Board queue and the Check-in tab's Waiting list) and on the Check-in tab's On a break rows, confirmed by `RemovePlayerDialog`) does the same from wherever they are, then takes them out of the queue and breaks and ends their locks; someone who has played stays in `players` so Standings and totals keep their results (`activeIds` is who is still taking part; a check-in by name brings them back under the same id), someone who has not is deleted. **On a court, Remove/break leave the spot open** (`removeFromCourt`): a team may then be shorter than the mode needs, the game is paused (`Court.pausedAt`, and `pausedSeconds` left out of the recorded time via `playedMs`), it cannot be finished (`isShort`) and staff fill the dashed spot (`fillCourtSpot`, from the queue or a break). Open spots keep their place: `Court.teams` stays a compact list and `Court.openSlots` says which positions are open (`courtSlots` gives the board order), so the tapped spot is the one filled. Short teams already pass the wire validator. **An open court can be set up by hand**: `fillCourtSpot` on it creates `teams` with `Court.notStarted` (players leave the queue but keep `queuedAt`; no time runs; Start game starts that exact line-up once full, `cancelMatch` is "Clear court"). **Next up spots can be pinned**: `nextUpPick` holds `null` for open spots (`fillNextUpSpot`, `nextUpSpots`); open spots fill automatically from the lane's queue once enough players wait. **Teams are shown as Blue and Orange** (`lib/teams.ts`, `--team-*` tokens in `index.css`), never "Team A/B"; index 0 is Blue. A pick with someone out of a level range stays in the lane that takes most of it.
- **Courts can be kept for skill levels** (`Court.levels`, min..max; missing = any level). `rotation/levels.ts` turns the courts into lanes (each distinct range in board order, then "any level" last) and `nextGroups()` in the engine gives each lane a group drawn only from in-range players that earlier lanes did not take (a locked pair only if both fit). `nextGroup(state, { courtId })` and `startGame` use the court's lane; `nextGroup(state)` without a court is still the whole-queue group, which is also what the "start with waiting players" override (`ignoreMode`) starts. With no level courts everything behaves as a single queue. Each court card has a staff ⋮ menu (`CourtMenu`, rules in `lib/courtMenu.ts`): Cancel game / Clear court, Rename…, Skill levels… (the same `CourtLevels` control as Manage courts), Move up / Move down, and Close court (asks first while a game is in progress; blocked for the only court). Manage courts keeps all of these plus Add court and the game length. The public snapshot carries `levels` per court and `nextUpLanes`, with `nextUp` = the first lane for older viewers.
- **Partners and opponents rotate in every mode** (`matchmaking/grouping.ts`). `pairHistory` reads the last `RECENT_MATCHES` games from `state.matches`; `selectGroup` adds `repeatPenalty` to a group's queue cost (so a foursome that just played counts as further back, in all four modes), and `splitGroup` picks the split with the fewest repeated partners, then opponents, among splits within `LOPSIDED_LIMIT` of the most balanced one (then smallest gap, then longest ago). Without this the tie-break kept `[a,b]` vs `[c,d]`, i.e. last game's partners, because teams rejoin the queue side by side. Locks and mixed-doubles rules are applied before any of it.
- **Repeat stats** (`rotation/repeats.ts`, `components/RepeatStats.tsx`) are derived purely from `session.matches` over the whole session, so saved sessions get them for free. `StandingsScreen` shows them only with `repeatStats` (staff Standings and Past sessions); the public viewer never passes it because the live snapshot has no game history.
- **Partner locks** have two forms: `partners` (in force) and `pendingPartners` (made while a partner was on a court or break; they take effect once both finish a game). In-force pairs stand at the *later* partner's queue spot so a lock never lets someone skip the line.
- **Games are finished with a score** (`recordScore`); `recordResult` (no score) remains in the engine but the UI does not use it. Ranking: wins, point differential, opponent strength, win rate, name (`rotation/standings.ts`).
- Skill levels are stored as 1 to 6 (`lib/skill.ts` maps them to names and USA Pickleball ratings). Changing the number range means migrating roster, sessions, history and the wire validator.

### Persisted shapes and migrations
`SessionState` is persisted in three places: localStorage (the running session), Dexie `history` records, and cloud backups. All go through `migrateSession(session, fromVersion)` in `store/migrate.ts`, so **any change to a persisted shape needs a `SESSION_STORE_VERSION` bump plus a migration step**, unless the new field is optional and absent means "none" (the pattern used for `nextUpPick`, `pendingPartners`). Store-level fields beside the session (`sessionId`, `startedAt`, `lifetimeCounted`) are migrated in the store's own `migrate`. Dexie schema versions are in `db/db.ts`.

### History, resume and all-time totals
Ending a session archives it (`db/history.ts`) whether or not results are saved. Deleting a past session is **soft**: the record gets `deletedAt` and `deletionPending` ('delete' / 'restore' / 'purge'), `syncHistory` sends pending ones after the uploads (`DELETE /history/:id`, `?permanent=1`, `POST …/restore`), and `mergeHistory` (`lib/pastSessions.ts`, pure) merges this device's and the club's lists so a delete or restore made on another device is followed (`followClubDeletion` / `followClubRestore`) unless a change here is still pending. The server keeps `session_history.deleted_at` (migration 009), hides deleted rows from `GET /history`, never undeletes on `PUT`, and removes rows deleted over `HISTORY_TRASH_DAYS` (30) ago. Saving to the all-time totals adds only `stats - lifetimeCounted` (`rotation/lifetime.ts`), so a resumed session never double counts, locally or on the club leaderboard. A session's player ids are **the session's own** (`sessionIdFor` in `store/actions.ts`: the same name keeps its id, anyone new gets `max + 1`), the same on every staff device; they are never a device's roster ids, so everything that links a session player to a saved one (avatars via `AvatarContext.local`/`rosterIds`, `saveLifetimeStats`, `lib/rename.ts`, `useSkillEditor`, `RosterCheckIn`) goes **by name** through `findSavedPlayer`. The roster itself is **per club and shared by all the club's devices**: each `Player` row carries `clubSlug`, every read and match goes through `listRoster(slug)` / `addOrGetPlayer(..., slug)` in `db/roster.ts` (no slug, in a build with no cloud, means the unclaimed rows), and `syncRoster` in `cloud/sync.ts` sends `rosterDirty` rows to `PUT /roster` and merges `GET /roster` back by lower-case name (`mergeClubRoster`: adds missing players with new local ids, takes the club's skill/gender unless the local row is still dirty). It runs in `runSync`, every 30 s while signed in, and debounced after a roster change (`requestRosterSync`). Unclaimed rows are taken by the first club to sync (`claimUnownedPlayers` in `adoptClub`). A player's **name is a copy** in the roster, the running session, ended sessions, the club leaderboard, the club roster and the club's avatars (the last three keyed by lower-case name). Rename only through `lib/rename.ts`: it updates the roster and the running session (ended sessions keep the old name) and queues `POST /players/rename` (`flushRenames` in `cloud/sync.ts`, stored in the Dexie `settings` table, sent before everything else in `runSync`, dropped when a different club logs in); it also rewrites names inside `pendingLifetime` so a queued upload cannot recreate the old row.

### Several sessions at once
A club can run **several sessions side by side** (API migration 010: `session_backups` and `live_sessions` are keyed by `(club_slug, session_id)`, each session with its own revision; `session_presence` says which staff devices have one open). On a device, the store's top-level fields are the **open** session and `parked` (`store/slices.ts`) holds sessions staff **left without ending** (`leaveSession`, `openSession`; creating, joining or resuming another parks the open one), each with its own `base`/`pending`, persisted, and tagged with the club signed in when it was left (`clubSlug`; `parkedFor`): only that club is sent it, lists it, or can end it, as with ended sessions. The sync sends parked sessions' unsent changes too (`sendSession` in `startCloudSync` is one path for open and parked; `confirmSlice`/`rebaseSlice` are the parked equivalents of `confirmPublished`/`rebaseOnto`), and archives a parked session the club no longer runs (`adoptParkedCopy`). `endedSessionIds` (was `endedSessionId`) lists ends not yet sent. `useSyncStore.clubSessions` is `GET /sessions` (polled, and refreshed on `revision`/`ended` events, which carry `sessionId`); the setup screen's **Open sessions** (`OpenSessionsCard`, `runningSessions` in `lib/openSessions.ts`) merges it with `parked`, and **Open** is `openRunningSession`. **Leaving** (`leaveOpenSession`) asks the club who has the session open (presence: `PUT /sessions/:id/presence` every 15 s while open, `DELETE` on leaving): it pauses (`pausedBy.reason = 'left'`) only when no other device has it open (or it cannot tell, or no cloud). A pause made on another device opens `PausedByDialog` (`pausedNoticeFor` in `lib/pause.ts`, keyed by `clockStoppedAt` so dismissing lasts for that pause only) and the banner stays (`SessionClockBanner`); a start or resume from another device is a toast (`statusChangeMessage`). Requests with no session id (older apps) mean the club's latest session. Live boards: `/club/<slug>/live/<sessionId>` (`liveBoardPath(slug, id)`, `liveSessionIdFromPath`; API `GET /clubs/:slug/live/:sessionId` and `/stream`, hub channel `slug/sessionId`); the club's own `/club/<slug>/live` shows its latest live session (older viewers and printed QR codes), offers a choice when several are live (`GET /clubs/:slug/lives`), and stays on the session it first showed. The club channel still gets `update`/`cleared` for the latest live board (older viewers), plus `revision` and `ended` (a new event name older apps ignore) for staff. `canonicalLiveBoardPath` keeps a session id. The public snapshot carries `status` (`notStarted`/`paused`), never who paused.

### Several staff devices, one session
Staff devices of a club can run one session together. Every store action is data (`SessionAction` in `store/actions.ts`, applied by `applyAction` with the same engine rules; undo is a `restore` that only applies from the exact state it undoes). While shared, the store keeps `base` (the club's copy and its revision) and `pending` (this device's actions the club has not taken); `session` is always `base` + `pending`, and both are persisted so offline changes survive a reload. `startCloudSync` sends with `baseRevision`; the API (`session_backups.revision`/`session_id`, migration 006) refuses a stale one with 409 `conflict` and the club's copy, and the device **rebases** (`rebase`: replays `pending` on it, renumbering ids a replayed check-in changed, dropping what no longer applies with a "Not applied" toast) and sends again. Other devices' changes arrive through the live stream's `revision` event (sent on every publish, live or not; viewers ignore it) plus a 15 s poll, then `GET /session/state` with the staff token (`adoptClubCopy`). Nothing is sent when nothing is pending, so a device never echoes the other's change back. The refresh fetches `GET /session/state?sessionId` for the open session only; a copy that disappears means it was ended elsewhere (`endedElsewhere`: archived here, marked synced, back to setup, or dropped from `parked`). Ending sends `DELETE /session?sessionId`, and `endedSessionIds` is persisted until that reaches the club, because the app can reload right after ending. Opening a session another device runs is `joinClubSession` (via `openRunningSession`). Sends and fetches run one at a time (`serially`), so a fetched copy is never mixed with a send in flight. Older cached apps send without `baseRevision` and stay last-write-wins.

### Going live
A session is on the public live page only while `SessionState.live !== false` and it has started (`isLive`; missing = live, for older sessions). `startSession` creates it with `live: false` and not started; staff choose **Go live** / **Stop live** in `SessionMenu` (the `setLive` action, shared and rebased like any other; undo keeps it). The publish sends `PublishMeta.live`; the API then deletes `live_sessions` (viewers get `cleared`) but still stores the backup and moves the revision, so staff devices keep sharing it. Cloud e2e specs that start a session in the UI and look at the public page must call `goLive` (`e2e/cloud/support.ts`). The setup button is **Create session**; the e2e `startSession` helper then presses **Start session**, so specs get a running session. `openFromList` opens one from the setup screen's list.

### Activity log (who did what)
Staff devices share one club password, so the log is per **device**: `lib/device.ts` gives each device a random id (`q2dink-device` in localStorage), its details (`deviceLabel`: Chrome on Android gives the model code, such as `SM-S918B`, through client hints; Apple devices only say "iPhone"/"iPad") and a **name** staff must give it after logging in (`DeviceNameGate`, `requiresDeviceName` in `cloud/gate.ts`). The club refuses a name another of its devices has (`club_devices`, unique on `lower(name)`, `409 name_taken`), so two identical phones never look the same. Every session action gets a readable line from `describeAction` (`store/auditText.ts`, pure). While the session is shared the entry rides on its `PendingAction.audit` and is only logged once the club took it (`confirmPublished`); a change a rebase drops is logged as "Not applied". Club events (session started/ended/resumed/joined, roster, avatars, photo sharing, renames, login/logout) go through `recordAudit` in `cloud/audit.ts`. Entries wait in the Dexie `auditQueue` (per club) and `flushAudit` (`cloud/sync.ts`) sends them to `POST /audit` (idempotent by id). `ActivityDialog` shows them (session menu, Past sessions, "Club activity" on setup) in numbered pages of 20 (`GET /audit?page` returns `total`) with a search (`q`: summary, device name or label; `likePattern` in `services/audit.ts` escapes wildcards, `matchesSearch` is the same rule on the device) and a device filter; this device's unsent entries show on page 1. The log is staff only and never in the live snapshot. A new `SessionAction` needs a case in `describeAction`.

### Avatars (clubs no longer have logos)
Avatars are deliberately **outside the session and the live snapshot** (photos would break the 256 KB backup and the localStorage budget). A player's avatar lives on the roster row (`Player.avatar`, Dexie, with an `avatarDirty` flag for pending uploads); the photo-sharing switch lives in the Dexie `settings` table. `lib/avatars.ts` resolves what to draw: this device's roster avatar by id, else the club's avatar by lower-case name (fetched from `GET /clubs/:slug/avatars` by `AvatarProvider`, also on the live page), else automatic initials. `syncMedia` in `cloud/sync.ts` uploads changes, **photos included, always**: the club's other staff devices take them into their own roster (`pullAvatars`, run after each roster sync: `GET /avatars` staff index, then `GET /avatars/:key` with the photo as base64, saved as a data URL with `avatarVersion` so an unchanged one is not fetched again; a local change not yet sent wins). "Show player photos on the live page" is a **club-wide** setting (`clubs.share_photos`, `PUT /photo-sharing`, mirrored in the Dexie `sharePhotos` setting): it only decides whether the public index and `/clubs/:slug/avatars/:key/photo` show photos (while off, a photo is listed as initials). `DELETE /avatars` is kept for older cached apps and only turns sharing off, never deletes. Picking a photo goes through a crop step first: the pure maths is in `lib/crop.ts` (`PhotoCropper` is the UI: drag and zoom under a round frame) and `processImage(file, crop?)` applies it (no crop = centred square). **Take photo** uses `getUserMedia` through `CameraCapture` on computers (`shouldUseInAppCamera` in `lib/camera.ts`: the API exists and the primary pointer is not touch) because browsers ignore the file input's `capture` hint outside phones; phones and tablets, and browsers without the API (plain HTTP), keep the hidden `capture` inputs. The captured frame goes through the same `handleFile` -> crop flow as a chosen file, the front-camera preview is mirrored with CSS only (the saved frame is not), and **every stream must be stopped** (`stopStream`) when the step goes away or the camera light stays on. The Permissions-Policy header already allows `camera=(self)`; the Playwright camera specs use Chromium's fake camera. Initials and emoji are drawn from `data-*` attributes with CSS `content`, so avatars add no text to the page (tests that read row text rely on this). **Club logos were removed**: migration 008 dropped `club_logos`, Dexie version 6 deletes a device's old `logo` setting, `PUT`/`DELETE /logo` stay as no-ops (204) for older cached apps, and the avatar index's `logo` is always `null`; the nav bar and shared cards show the Q2Dink mark.

### Cloud and the wire contract
When a cloud is configured (`VITE_API_URL`), the app is **gated by a club login**: `App.tsx` shows `LoginGate` (via `requiresLogin` in `cloud/gate.ts`) until `useClubAuth` has a club, except on the public `/club/<slug>/live` viewer (`liveBoardPath` in `packages/shared/src/slug.ts`; the older `/club/<slug>` still opens it, and `main.tsx` rewrites the address bar to the `/live` form). The saved token keeps the app usable offline; `checkLogin` in `cloud/sync.ts` asks the server once at launch and when the connection returns, and only an `invalid_token` answer signs out. A build with no API has no login (the local e2e projects rely on this). A new recovery code is held in `cloud/recovery.ts` and shown by `RecoveryCodeHost` in `App`, because creating a club replaces the login screen under the dialog that made it.

`packages/shared` defines everything that crosses HTTP: `PublicSnapshot` (what the public `/club/<slug>/live` page shows; genders and results history are deliberately excluded), `FullBackupEnvelope` (private, for resuming), history and lifetime requests. The web app talks only to the `CloudApi` interface (`cloud/api.ts`; `httpApi.ts` implements it); `cloud/sync.ts` and `cloud/publisher.ts` publish the running session (debounced, offline-tolerant) and `syncHistory` uploads ended sessions. The API validates through the shared parsers, which return a **fresh copy with only known fields**. When adding a wire field, make it optional on input and default it in the copy so an older cached web app can still publish. The viewer page reuses the staff components in read-only mode (no callbacks passed).

`apps/api`: routes in `src/routes`, logic in `src/services`, TypeScript migrations in `src/db/migrations.ts` (append only; a test lists the expected tables), PGlite in dev and tests, real Postgres in production.

### Reset this device
`ResetDeviceDialog` (next to Log out in `ClubPanel`; in the setup list for a build with no cloud) wipes the device: `resetDevice` in `lib/reset.ts` ends the login on the server (best effort), deletes the `q2dink` IndexedDB database and removes `LOCAL_STORAGE_KEYS_TO_CLEAR` (the session and the club login), then the page reloads. It keeps `q2dink-device` (the same device keeps its id and registered name, which would otherwise be "taken") and display preferences. Before resetting, `countUnsent` (`cloud/sync.ts`) lists what the club has not been sent (`unsentChanges`), with "Try sending first" (`sendEverythingNow`). A new place that keeps unsent data on the device should be counted there.

### Several clubs on one device
Past sessions and totals live on the device, and roster rows are tagged with their club (only the signed-in club's players are listed; another club's stay on the device, hidden, until it logs in again). What is *sent* to a club must only be that club's. Ended sessions carry `clubSlug` (`db/history.ts`; `syncHistory` sends `unsyncedHistory(slug)`, i.e. the club's own plus older ones no club has claimed, which the first club to sync takes). Pending all-time totals are tagged by slug. The avatar "dirty" flags carry no club, so `adoptClub` (called at the start of `syncMedia`) remembers which club they are for (`syncClub` in `settings`): when a different club logs in, the earlier club's unsent avatar changes and photo switch are dropped (the new club's own switch arrives with its next sync).

### Security headers
The Content-Security-Policy is defined once in `apps/web/csp.ts`, copied into `deploy/Caddyfile` (`csp.test.ts` fails if they differ), and served by `vite preview`, so the whole Playwright suite runs under the production policy. `e2e/cspWatch.ts` (`failOnCspViolations(test)`) fails any test whose page logs a violation; the cloud specs use it. A new kind of resource (an external font, an inline script, a remote image) needs a deliberate policy change in both places. The service worker's navigation fallback must never catch `/api` (`navigateFallbackDenylist` in `vite.config.ts`).

### Renamed from Matchup
The product used to be called Matchup (repo `matchup`, npm scope `@matchup`, IndexedDB `matchup`, localStorage `matchup-session` / `matchup-club`). It is **Q2Dink** now (repo `q2dink`, scope `@q2dink`, `q2dink`, `q2dink-session` / `q2dink-club`). Browsers cannot rename storage, so `lib/legacyStorage.ts` (called first from `main.tsx` via `legacy.ts`) and `db/legacyMigration.ts` (Dexie's `ready` hook in `db/db.ts`) move an old device's data across on first launch, and they are the only source files that may still contain the old names (plus `docs/pickleq-specs.md`, which documents another product, and the "Upgrading from Matchup" section of `deploy/README.md`: servers set up before the rename keep `POSTGRES_USER=matchup` / `POSTGRES_DB=matchup`). `topMatchup` in `rotation/repeats.ts` is the ordinary word (a pairing of opponents), not the product name.

### Light and dark theme
The theme is `next-themes` (`ThemeProvider` in `main.tsx`, class `dark` on `<html>`, choice stored under the key `theme`, default System) with the `.dark` colour tokens in `index.css`; `ThemeSwitch` (one per screen, rendered in `App.tsx`) chooses Light/Dark/System and keeps `<meta name="theme-color">` in step. **`public/theme-init.js` must stay an external file**: it sets the class before first paint, and the Content-Security-Policy (`script-src 'self'`) blocks the inline script `next-themes` would otherwise use, which would flash white for dark-mode users. `lib/theme.test.ts` runs that script against the same cases as `isDark`, so change both together. Colours must come from the tokens (`bg-background`, `text-muted-foreground`, ...), not fixed ones, so both themes work.

### Version
The version has one source of truth: `version` in the **root** `package.json` (bump with `npm version minor --no-git-tag-version` at the root; workspace versions are unused). `vite.config.ts` (web) and `tsup.config.ts` (API) inject it with `define` along with the short commit (`GIT_SHA` env, else `git rev-parse`, else `dev`) and build date. Docker builds cannot see `.git`, so both Dockerfiles take a `GIT_SHA` build arg (the prod compose file and CI pass it). The web app renders it once in `App.tsx` (`VersionLabel`, `lib/version.ts`); the API reports it on `GET /api/health`. Running from source (tests, tsx) reports `dev` for the API.

**When to bump** (decide it yourself; don't ask). Bump in the same commit as the change, or in a separate "Bump to x.y.z" commit right after it, before pushing:
- **Minor** (`npm version minor`): a new feature or visible behaviour change, a new API route or wire field, or any database migration (API or Dexie). This includes a batch of smaller UI changes going out together.
- **Patch** (`npm version patch`): bug fixes and small UI or copy tweaks with no migration and no new route.
- **Major**: only when an older cached web app or an existing server could no longer work with the new one, or stored data must be converted in a way that can't be read back. That's rare, so check with the user first.
- **No bump**: changes only to tests, docs, CI or tooling (nothing a device or server would run differently).

The header shows only the version, so without a bump two builds look the same on a phone.

## Conventions and pitfalls

- **Every feature and bug fix comes with unit tests** (Vitest, next to the code: `*.test.ts`), not only e2e. Put the logic where it can be tested without a browser (the engine, `lib/`, `db/`, `cloud/`) and test it there; for a bug, write the failing test first. E2E specs are in addition, for the flow through the UI.
- Tests that need a running board start games explicitly (`startGame`/`fillCourts`), never rely on check-in doing it. The store's `startSession` creates a session **not started**: store tests that play call `startClock` too (`startRunning` in `store/session.test.ts`); engine tests use `createSession` directly, which is running.
- The device id (`q2dink-device`) is saved on first launch (`keepDeviceId`): a pause is attributed by it, and a new id after a reload would show this device's own pause as another device's. E2E helpers live in `apps/web/e2e/helpers.ts` (`startSession`, `checkIn`, `startGame`, `recordWin`, `cancelGame`).
- Cloud e2e: after logging in the app asks to name the device; `uiLogin`, `confirmRecoveryCode` and `expectSignedIn` in `e2e/cloud/support.ts` name it (`nameDevice`) when asked, so a spec that logs in another way must call one of them.
- E2E gotchas: Sonner toasts linger about 10 seconds, so `getByText('Court 1: Team A won')` can match twice; Radix Tabs unmount inactive tabs (switch to Board before looking for court controls); while a dialog is open, `getByRole` cannot see the page behind it (aria-hidden); the Next up card contains list items, so scope queue rows with `ol > li`.
- The working tree can be CRLF on Windows. When scripting edits, normalise line endings first. Avoid backticks and `$'` in shell heredocs or `node -e` strings; use the editor tools for code containing template literals.
- Commit and push only when asked.
